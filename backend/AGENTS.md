# Backend AI Coding Guidelines

These instructions apply to the entire `backend/` directory. Follow the existing project conventions before introducing new patterns or dependencies.

## Project Structure

- Java 21, Spring Boot 4.x; base package: `com.fashionstore.backend`.
- Keep application code under `src/main/java/com/fashionstore/backend`.
- Put HTTP endpoints in `controller`, business rules in `service`, JPA entities in `entity`, Spring Data interfaces in `repository`, MapStruct interfaces in `mapper`, request/response models in `dto/request` and `dto/response`, and application exceptions in `exception`.
- Put Spring configuration classes in `configuration`.
- Do not duplicate an existing class or move code across layers without a clear reason.

## Naming and Database Mapping

- Use English names for Java classes, methods, fields, DTO properties, and API paths. Use Vietnamese only where required by existing API wording or the database schema.
- Preserve SQL Server table and column names exactly. Map them explicitly with `@Table(name = "...", schema = "dbo")` and `@Column(name = "...")`; never rely on Hibernate naming to translate English properties into database identifiers.
- The existing database is SQL Server `Fashion_Q1`; do not create or alter tables as part of ordinary feature work.
- Keep `spring.jpa.hibernate.ddl-auto=none`. Do not change database, schema, or profile configuration to make an entity appear to work.
- `TaiKhoan.MaTaiKhoan` is an SQL Server `INT IDENTITY`; map it with `@GeneratedValue(strategy = GenerationType.IDENTITY)`. `NhanVien.MaNhanVien` and `ChiNhanh.MaChiNhanh` are `VARCHAR(10)` primary keys generated by their services as `NV`/`CN` plus an eight-digit sequence (for example, `NV00000001`); do not require these IDs in create requests or add JPA `IDENTITY` to the string columns. `NhanVien.MaChiNhanh` is a foreign key and must be provided from an existing branch when creating an employee.
- Prefer Spring Data JPA for normal persistence and existence checks. Add or reuse an Entity/Repository when appropriate; do not introduce `JdbcTemplate` queries for operations that JPA can express cleanly.
- Keep credentials out of source code and logs. Use environment variables or the established local configuration mechanism; never copy secrets into documentation or generated examples.

## Entities and Lombok

- JPA entities use explicit `@Entity` and `@Table` mappings and the project's Lombok style: `@NoArgsConstructor(access = AccessLevel.PROTECTED)`, `@AllArgsConstructor`, `@Builder`, `@FieldDefaults(level = AccessLevel.PRIVATE)`, and `@Data` where consistent with the entity.
- Keep a protected no-argument constructor for JPA. Initialize database-defaulted fields deliberately when entities are created through a builder; do not assume SQL Server defaults are applied if Hibernate sends an explicit `NULL`.
- Exclude credentials or other secrets from generated `toString()` output with `@ToString.Exclude`.
- Preserve primary-key type, nullability, lengths, and SQL data types from the actual database schema.

## DTOs and Mapping

- Use request and response DTOs; do not expose JPA entities directly from controllers.
- Use Java records for simple DTOs and Jakarta Bean Validation annotations for request constraints (`@NotBlank`, `@NotNull`, `@Size`, `@Email`, etc.). Match limits and nullability to the database.
- Use MapStruct mapper interfaces annotated with `@Mapper(componentModel = "spring")`. Add explicit `@Mapping` declarations for defaults, differently named fields, or intentional omissions.
- Do not write repetitive manual entity/DTO conversion in services when a MapStruct mapper is appropriate. Keep MapStruct and Lombok annotation-processor configuration in `pom.xml` intact.

## Repositories and Services

- Repository interfaces extend the narrowest suitable Spring Data interface, usually `JpaRepository<Entity, IdType>`, and use `@Repository` to match the current project style.
- Services use `@Service`, `@RequiredArgsConstructor`, and `@FieldDefaults(level = AccessLevel.PRIVATE, makeFinal = true)` for constructor injection. Avoid field injection and handwritten constructors for required dependencies.
- Put validation of business rules and cross-repository checks in services. Keep controllers focused on HTTP concerns.
- Throw `AppException` with an appropriate `ErrorCode` for expected business errors. Add new error codes with the intended HTTP status; do not introduce ad hoc exception handling in individual controllers.

## Controllers and API Responses

- Controllers use `@RestController`, a resource-oriented `@RequestMapping`, `@RequiredArgsConstructor`, and `@FieldDefaults(level = AccessLevel.PRIVATE, makeFinal = true)`.
- Return the existing `ApiResponse<T>` wrapper, usually inside `ResponseEntity`, and set the appropriate HTTP status (for example, `201 Created` after creation).
- Validate request bodies with `@Valid @RequestBody`.
- Document controllers with `@Tag`; use Vietnamese tag names and descriptions. Document individual endpoints with `@Operation` summaries.
- Keep API paths and DTO properties in English, consistent with the current `employees`, `accounts`, and `roles` endpoints.

## Exceptions

- Reuse `AppException`, `ErrorCode`, and `GlobalExceptionHandler` in `exception`.
- Keep HTTP status, stable application error code, and user-facing message together in `ErrorCode`.
- `GlobalExceptionHandler` is responsible for translating application and validation exceptions into `ApiResponse`; do not return stack traces or internal exception details to clients.
- Log unexpected exceptions server-side and return the generic error code/message to clients.

## Security and Configuration

- Do not disable or bypass security to make an endpoint work. Before adding authorization annotations, verify that the application has the corresponding Spring Security configuration.
- `spring-security-crypto` is available for password hashing; never return or log passwords or password hashes.
- Do not change `application.properties` or `application-local.properties` unrelated to the requested feature. Never print credential values in terminal output, responses, or documentation.

## Validation

- Run Maven from `backend/` using the wrapper: `sh ./mvnw -DskipTests compile` for a quick compile check or `sh ./mvnw -DskipTests package` for packaging.
- Run focused tests first when tests exist. Do not claim that an endpoint or database connection was runtime-tested unless it was actually started and exercised against the configured database.
